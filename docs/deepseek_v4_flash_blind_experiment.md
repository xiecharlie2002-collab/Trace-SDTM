# DeepSeek V4 Flash 盲评实验结果

## 实验定位

本实验评价大模型根据原始字段画像提出 SDTM 候选映射的能力。模型只看到映射任务编号、来源数据集、来源字段、原始字段画像、允许的 SDTM 变量和受控函数白名单；模型看不到专家模板中的目标变量、映射类型或转换函数。

模型为 `deepseek-v4-flash`，提示设计标记为 `blind_source_only_v1`。实验日期为 2026-09-01。40 个任务来自 DM、AE、VS 的专家金标准。该样本用于作品集演示，不代表其他研究、其他原始数据结构或其他模型版本的总体表现。

第一次真实调用存在答案泄漏，已经单独标记为无效实验，不纳入以下统计。

## 两层正确性口径

核心映射正确要求目标域、目标变量、目标常量值和转换函数均与金标准一致。

可直接执行的完全正确在核心映射正确基础上，还要求映射类型和转换参数与项目登记的函数契约一致。人工审核中的“接受”采用这一更严格口径。

## 主要结果

模型为 40/40 个任务提供了首选候选，共生成 61 条候选。25 个任务只有一个候选，9 个任务有两个候选，6 个任务有三个候选。

| 指标 | 结果 |
|---|---:|
| 获得首选候选的任务 | 40/40（100.0%） |
| 首选核心映射正确 | 28/40（70.0%） |
| 前三项核心映射命中 | 28/40（70.0%） |
| 首选完全正确 | 11/40（27.5%） |
| 前三项完全命中 | 11/40（27.5%） |
| 人工直接接受 | 11/40（27.5%） |
| 人工修改后接受 | 29/40（72.5%） |
| 人工拒绝 | 0/40（0.0%） |
| 信息不足 | 0/40（0.0%） |

拒绝数为 0，不表示模型没有错误。评价集中的每个任务都来自应当实现的金标准映射，因此错误首选被修改为金标准，而不是删除任务。

模型没有从第二或第三候选中增加任何命中。尤其在 VS 纵向转换任务中，备选仍集中在 `VSORRES`、`VSSTRESN` 和 `VSSTRESC`，没有识别出本项目所需的 `VSTESTCD` 常量映射。

## 按域结果

| 域 | 核心映射正确 | 完全正确 | 结论 |
|---|---:|---:|---|
| DM | 13/15（86.7%） | 8/15（53.3%） | 三个域中最好；SITEID 和 USUBJID 派生仍需人工判断 |
| AE | 10/13（76.9%） | 1/13（7.7%） | 目标选择多数正确，但术语表、日期格式和派生参数不符合函数契约 |
| VS | 5/12（41.7%） | 2/12（16.7%） | 最难；主要失败于横向测量字段转为纵向记录的语义 |

VS 是本次实验最难的域。困难不主要来自变量名称，而来自一条原始记录如何拆成多条 Findings 记录，以及 `VSTESTCD`、`VSTEST`、结果值、单位之间的联动规则。

## 按映射难度结果

| 映射难度 | 核心映射正确 | 完全正确 | 解释 |
|---|---:|---:|---|
| 直接映射 | 13/13（100.0%） | 11/13（84.6%） | 最稳定；少数候选加入了项目不需要的参数 |
| 受控术语转换 | 8/8（100.0%） | 0/8（0.0%） | 能识别需要术语转换，但参数键名、术语覆盖或具体目标值不符合本地函数契约 |
| 日期转换 | 5/5（100.0%） | 0/5（0.0%） | 能选对日期变量和函数，但经常只猜一个输入格式，且格式判断与原始数据不一致 |
| 派生映射 | 2/8（25.0%） | 0/8（0.0%） | 对 USUBJID、SITEID、AEENRF 等依赖上下文的规则识别较弱 |
| 纵向转换 | 0/6（0.0%） | 0/6（0.0%） | 把测量字段理解为结果变量，未形成完整的纵向记录生成方案 |

这里出现“核心映射正确但完全正确为 0”的情况，说明模型理解了业务概念，却没有掌握本项目函数库的精确参数协议。它适合提出候选，不适合未经审核直接生成正式规格。

## 常见错误

一条任务可能同时包含多类错误，因此以下计数不能相加作为错误任务总数。

| 错误组成 | 出现任务数 |
|---|---:|
| 转换参数不符合函数契约 | 25/40 |
| 转换函数选择错误 | 10/40 |
| 目标变量错误 | 8/40 |
| 映射类型错误 | 7/40 |
| 目标常量值错误 | 6/40 |
| 目标域错误 | 0/40 |

最常见问题有四类：

1. 使用看似合理但项目无法执行的参数名称。例如把受控术语字典写在 `mapping` 下，而登记函数要求 `terms`；日期转换使用单个 `source_format`，而项目要求候选格式列表。
2. 对派生规则缺少研究上下文。模型把 SITEID 误判成 USUBJID，把 AEENRF 误判成 AEENDTC。
3. 不理解 Findings 类域的纵向生成粒度。身高、体重、体温和血压字段被映射到结果变量，而不是用 `VSTESTCD` 常量驱动整条记录生成。
4. 置信度量纲不一致。61 条候选中有 29 条使用 8、9、90、95 等大于 1 的值，其余候选使用 0 到 1，说明后续版本必须在结构约束中强制统一范围。

## 审核后验证

29 条错误或不完整的首选建议已按金标准修改，审核规格随后用于确定性构建。最终生成 DM 6 行、AE 8 行、VS 60 行。

- 本地检查：0 个问题。
- Pinnacle 21 Community：31 个问题，全部归类为最小项目范围导致。
- `generated_domain_defect`：0 个。
- Reject：2 个，分别为缺少 Define-XML 和缺少 TS。

这些验证结果属于“人工审核修正后的规格”，不能表述为模型原始输出直接通过 Pinnacle 21。

## 可写进简历的结论

更可信的表述是：构建受约束、可断点续跑的大模型辅助 SDTM 映射流程，在 40 项盲评任务上获得 28/40 的核心首选命中；严格考虑本地转换函数参数后，11/40 可直接接受。错误主要集中于纵向转换、派生规则和函数参数契约。经人工审核修正后，系统可重复生成 DM、AE、VS，并完成本地检查和 Pinnacle 21 Community 验证。

不应写成“模型自动生成 SDTM，准确率 70%”或“模型输出直接通过合规验证”。
